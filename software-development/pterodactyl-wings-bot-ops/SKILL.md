# Pterodactyl Wings Bot Ops

Operate Pterodactyl-hosted bots from the agent terminal on the same host. Works for any
server type (WhatsApp Baileys selfbot, Discord, game server, web app) — the access pattern is identical.

## When to use
- User says "bot di Pterodactyl", "server di pterodactyl", "edit file server bot", "panel gak bisa dibuka/konek".
- You need to read/edit files inside a Pterodactyl server container from the host.
- The Pterodactyl panel shows "Could not establish a connection to the machine running this server."

## Key facts (WSL/Linux host)
- Server files live at `/var/lib/pterodactyl/volumes/<server-uuid>/` — **root-owned**, not the agent user.
- `sudo` may need `NOPASSWD` for the agent user. One-liner the user runs once:
  `echo 'satzz ALL=(ALL) NOPASSWD:ALL' | sudo tee /etc/sudoers.d/satzz`
  Then `sudo docker ps`, `sudo cat /etc/pterodactyl/config.yml`, etc. work non-interactively.
- Wings daemon listens on `:8080` (HTTPS, self-signed / LetsEncrypt), SFTP on `:2022`.
- Wings config: `/etc/pterodactyl/config.yml` (token_id + token for daemon API calls).

## Workflow: edit a bot's files safely
1. Find the container: `sudo docker ps` → copy the NAME (it is the server UUID like `ad395f3d-...`).
2. Copy the target file to a user-writable dir, chown it, edit, then copy back:
   ```
   sudo cp /var/lib/pterodactyl/volumes/<uuid>/commands/foo.js /home/satzz/edit/
   sudo chown satzz:satzz /home/satzz/edit/foo.js
   # patch with write_file/patch
   sudo cp /home/satzz/edit/foo.js /var/lib/pterodactyl/volumes/<uuid>/commands/foo.js
   ```
   Use a loop for globbed multi-file copies — `sudo cp dir/*.js dest/` fails because the
   shell glob does not expand under sudo for non-root-owned source dirs.
   `for f in $(sudo ls dir/); do sudo cp "dir/$f" dest/; done`
3. Syntax-check before copying back: `node --check file.js` (node may live in user PATH, not sudo PATH).
4. If the container runs via `node runner.js` → **nodemon** (check `ps aux | grep nodemon`),
   file saves auto-restart the bot. Confirm in `docker logs --since 60s <uuid>` for
   `[nodemon] restarting due to changes...` + `<N> command(s) loaded`. **Do NOT build a
   `.restart` command — it is redundant when nodemon is in use.**

## Fix: "Could not establish a connection to the machine running this server"
Panel PHP (Laravel) cannot reach the Wings daemon. Symptom in `storage/logs/laravel-*.log`:
`cURL error 28: Connection timed out ... for https://node.<domain>:8080/...`.
Root cause: `node.<domain>` resolves to the PUBLIC IP and cannot hairpin back to WSL.
The daemon itself is healthy (test: `curl -sk -I https://node.<domain>:8080/api/system` → 401).

**Fix:** add a localhost mapping in `/etc/hosts` (panel still uses the FQDN, so the
LetsEncrypt cert stays valid, but the connection stays on-loopback):
```bash
echo "127.0.0.1 node.<domain>" | sudo tee -a /etc/hosts
```
Verify: `curl -sS -o /dev/null -w "%{http_code} %{time_total}\n" https://node.<domain>:8080/api/system`
→ should return `401 0.0x` (fast, local). The panel File Manager / Console now work again.
Pitfall: this `/etc/hosts` entry is regenerated by WSL on full reset — re-apply if the error returns.

## Fix: ERR_SSL_PROTOCOL_ERROR on `https://node.<domain>:8080/...` when behind a Cloudflare Tunnel
When the node sits behind a Cloudflare Tunnel (or any proxy), the browser talks
HTTPS to the public name. The Pterodactyl panel builds that URL from the node row's
**`daemonListen`** column. This session had `daemonListen = 8080`, so the panel JS emitted
`https://node.satzz.online:8080/api/system` — Cloudflare only terminates TLS on port 443, so
port 8080 gave `ERR_SSL_PROTOCOL_ERROR` / `ERR_CONNECTION_REFUSED`. Cloudflare does NOT proxy
non-443 TLS by default.

**Fix (validated via DB write):**
```bash
cd /var/www/pterodactyl
php -r 'include "vendor/autoload.php"; $app=require "bootstrap/app.php";
 $k=$app->make(Illuminate\Contracts\Console\Kernel::class); $k->bootstrap();
 DB::table("nodes")->where("id",1)->update(["daemonListen"=>443]);'
php artisan optimize:clear
# restart wings + cloudflared:
sudo systemctl restart wings cloudflared
```
After that the panel JS fetches `https://node.satzz.online/api/system` (port 443 → tunnel →
Wings localhost:8080). The node row needs `scheme=https`, `behind_proxy=1`, `fqdn=node.<domain>`.
This is a *client-visible* fix; the daemon continues to listen on 8080 internally.

## Command & dispatcher gotchas (this host's Baileys selfbot)
- **Real `run` signature is 5 args: `run(sock, m, args, reply, chat)`** — `chat` is the jid to pass to
  `sock.sendMessage(chat, ...)`. The starter template and many older notes show only 4 (missing `chat`).
- **`owner: true` is NOT enforced by the dispatcher.** `events/message.upsert.js` only gates `>>` (eval)
  and `$` (exec) via `RCE_NUMBERS`. Any `AUTHORIZED_NUMBERS` user or allowed chat can invoke a command
  flagged `owner: true`. Self-guard at the top of `run()`:
  ```js
  const senderNumber = (m.sender || "").split("@")[0];
  const isOwner = m.fromMe || (config.RCE_NUMBERS || []).includes(senderNumber);
  if (!isOwner) return reply("❌ Perintah ini hanya untuk owner.");
  ```
- **No `storeZip` helper exists** in `lib/helper.js`. For a `.backup` command, shell out to `zip`
  (already installed in the container) via `child_process.exec`, exclude `.npm`, `node_modules`,
  `session`, `tmp`, `.git`, then send the zip back with `sock.sendMessage(chat, { document: { url: outPath }, fileName, mimetype: "application/zip", caption }, { quoted: m })`. Bail if `fs.statSync(outPath).size > 100MB` (WA upload cap).
- **Sending files:** `reply()` is text-only. Use `sock.sendMessage(chat, {...}, {quoted:m})` for media/docs.
- `node --check` rejects non-`.js` draft files — copy drafts to `*.js` before syntax-checking.
- **read_file fails on root-owned volume files** ("File not found" even though `sudo cat` shows it).
  Use `sudo cat file | sudo tee /home/satzz/edit/file` then read the copy.
- **Don't rely on the web panel** when it 500s — go through disk files or the daemon API.
- **RCE in selfbots:** commands using `eval(...)`/`exec(...)` on `>>` / `$` prefixes must be gated
  to a real-owner list (e.g. `RCE_NUMBERS` in config), NOT the general `AUTHORIZED_NUMBERS` allowlist,
  or any allowed user gains full shell/RCE on the host.
- **`const trueFileName` bug pattern:** in Baileys download helpers, `trueFileName = ...` without
  `const`/`let` leaks to global scope and corrupts concurrent downloads. Always declare it.

## Inside-container binaries are INVISIBLE to the bot (host tools don't exist)
The Pterodactyl container is an isolated filesystem. A binary you installed on the WSL **host**
(e.g. `yt-dlp` at `/home/satzz/bin/yt-dlp`) is NOT visible inside the container, and neither is
anything in the host PATH. So `child_process.exec("yt-dlp ...")` from a command fails with
`/bin/sh: 1: yt-dlp: not found`, and `docker exec ... which yt-dlp` returns nothing.

**Reliable fix (persistent):**
1. Install the binary **into the volume mount** `/home/container/` (it is bind-mounted from the
   host volume, so it survives container restarts — unlike `/usr/local/bin` which is read-only in
   the image layer). For `yt-dlp` use the standalone Python zipapp (no pip needed in the container):
   ```bash
   sudo docker exec <uuid> bash -c "cd /home/container && curl -sL \
     https://github.com/yt-dlp/yt-dlp/releases/latest/download/yt-dlp -o yt-dlp \
     && chmod +x yt-dlp && ./yt-dlp --version"
   ```
2. Call it by **absolute path** `/home/container/yt-dlp`, OR inject PATH into the exec/spawn call:
   ```js
   exec(code, { env: { ...process.env, PATH: `/home/container:${process.env.PATH || ""}` } }, cb);
   ```
3. **Pitfall — `process.env.PATH` set in `runner.js` does NOT reach the bot.** Verified: the
   container's `entrypoint.sh` runs `eval ${STARTUP}` (STARTUP = `node .../index.js`), and the
   spawned bot process's `/proc/<pid>/environ` still showed the default container PATH without
   `/home/container`. The only reliable injection point is the `env` option on the actual
   `child_process.exec`/`spawn` call. If you want `$ yt-dlp` (the RCE eval/exec handler) to find it,
   patch the `$` block in `events/message.upsert.js` to pass that `env`.
- `ffmpeg` is already present at `/usr/bin/ffmpeg` in this container image (good for yt-dlp post-processing).

## Verify by ACTUALLY executing the function inside the container
Do NOT declare a command "working" on the strength of `node --check` + a clean nodemon reload
alone. This session shipped two false positives that way (the dlpanda `instaDL` returned `[]` at
runtime; a `.tmp` syntax check kept erroring). Before reporting success:
1. `node --check` the draft (copied to `*.js` first — `.tmp` is rejected).
2. `sudo cp` into the volume, confirm nodemon reload (`docker logs --since 60s <uuid>` shows the
   command in `<N> command(s) loaded` and no `Handler error`).
3. **Run the real logic in-container with a live payload**, e.g.:
   ```bash
   sudo docker cp /home/satzz/_probe.js <uuid>:/home/container/_probe.js
   sudo docker exec <uuid> bash -c "cd /home/container && node _probe.js"
   sudo docker exec <uuid> bash -c "rm -f /home/container/_probe.js"
   ```
   Test the actual export: `const {instaDL}=require('./lib/downloader'); ...`. For a command that
   needs `sock`/`m`, at minimum exercise the pure logic (regex, fuzzy match, file read) standalone.
4. Only then tell the user it works — and note explicitly if end-to-end (real WA media) is untested.

## Create a new server via the Panel Application API
When you need to spin up a *new* Pterodactyl server (e.g. a second WhatsApp bot), use the
Panel Application API directly from the host — no web UI needed:

```bash
# 1. (One-time) Allocate a new port on the node
curl -s -X POST \
  -H "Authorization: Bearer <ptla-key-with-admin>" \
  -H "Accept: application/json" -H "Content-Type: application/json" \
  "https://panel.<domain>/api/application/nodes/<node-id>/allocations" \
  -d '{"ip":"0.0.0.0","ports":["2001"]}'
# → 204 No Content on success. Read back with GET /allocations to get the new allocation ID.

# 2. Create the server
curl -s -X POST \
  -H "Authorization: Bearer <ptla-key-with-admin>" \
  -H "Accept: application/json" -H "Content-Type: application/json" \
  "https://panel.<domain>/api/application/servers" \
  -d '{
    "name":"Public Bot",
    "user":1,
    "egg":15,
    "docker_image":"ghcr.io/ptero-eggs/yolks:nodejs_22",
    "startup":"${STARTUP_COMMAND}",
    "environment":{"STARTUP_COMMAND":"node runner.js"},
    "allocation":{"default":<new-alloc-id>},
    "limits":{"memory":1024,"disk":2048,"io":0,"cpu":0},
    "deploy":{"locations":[],"panel":{"port":80},
              "env":{"STARTUP_COMMAND":"node runner.js"},
              "start_on_creation":true}
  }'
# → 201 on success; response JSON includes the server UUID.
```

**Pitfalls:**
- The admin `ptla_*` key must have **Application API** admin-level permissions. A key without them
  returns `403 Unauthorized` / `NotFoundHttpException` on `POST /servers`. This session had two keys;
  only the second (`ptla_OWpRF2...`) had admin access.
- `allocation.default` requires the **allocation ID** (not just a port number). Fetch it first via
  `GET /api/application/nodes/<node>/allocations`.
- The server is **not started** by the API call alone — either pass `deploy.start_on_creation: true`,
  or start it afterwards. This Pterodactyl stack (1.x) does NOT support `POST /api/application/servers/<id>/power`
  (returns `405 Method Not Allowed`). Use the **Wings daemon REST API** instead:
  `POST https://node.<domain>:8080/api/servers/<uuid>/power {'signal':'start'}` (see daemon-api.md).
- After creation, Wings auto-pulls the Docker image and runs the egg's install script. If the
  install hangs (e.g. `npm install` in an empty `/home/container`), kill the stuck container with
  `sudo docker rm -f <uuid>` then start fresh once files are copied in.

## Deploying a Wings node on the SAME host as the panel (co-located)
Full recipe + verified sequence + crash signatures + HARD-WON pitfalls: **`references/wings-node-deploy.md`**.
Key gotchas captured there (each one caused hours of looping this session):
- **CORS #1:** `remote: http://127.0.0.1` "fixes" boot DNS crash BUT sets
  `Access-Control-Allow-Origin: http://127.0.0.1` → panel (served from `https://panel.<domain>`)
  gets CORS-blocked, node shows RED even though curl returns 200. Use `remote: https://panel.<domain>`.
- **Glob #2:** `curl -H "Authorization: Bearer *** → `***` expands to filenames → token garbage → 403.
  Capture token to a var and quote: `TOK=$(...); curl -H "Authorization: Bearer $TOK"`.
- **Remote-managed tunnel #3:** if Zero Trust dashboard shows only "migration", local `config.yml`
  ingress is IGNORED by the edge. Click "Migrate" first or set `config_src=local` via API.
- **DecryptException #4:** `APP_KEY` without `base64:` prefix → `daemon_token` undecryptable → node red.
- **`/etc/hosts` node entry #5:** `127.0.0.1 nodes.<domain>` makes VPS-side curl resolve to localhost
  → `Failed to connect`. Remove it; keep only `127.0.0.1 panel.<domain>`.
- **daemonListen vs api.port #6:** `daemonListen` (DB) = port PANEL uses = 443 (tunnel TLS);
  `api.port` (config.yml) = port WINGS binds = 8080. Don't set both the same.
- Cloudflare Tunnel only proxies TLS on :443 by default — do NOT expose `:8080` publicly.
- Docker network pool overlap → `FATAL: ... Pool overlaps with other one on this address space`: add a
  `docker:` subnet (e.g. `172.21.0.0/16`) to config.yml that isn't used by existing docker networks.
- DNS CNAME MUST be in the zone that matches the FQDN (`satzz.online` vs `saturia.codes`). A CNAME in the
  wrong zone makes `dig +short CNAME <host>` return empty even though "it's in the dashboard".

## Verify-before-claiming-success discipline (USER PREFERENCE, repeated, firm)
NEVER declare "done / fixed / connected / works" without actual positive tool output proving it.
- For a Wings node: prove with `curl .../api/system` -> `200` (or at least `401` locally) and
  `dig @1.1.1.1 +short CNAME <host>` showing the tunnel target. Empty `dig` or `Could not resolve host`
  means NOT connected — fix DNS/tunnel before claiming success.
- Do NOT guess, assume, or conclude on your own ("ngarang"). State only verified facts. If blocked
  (e.g. can't read a token file, DNS not propagating), say so honestly instead of inventing a success.
- When the user says "udah bener" / "gw udah bikin" — trust them, stop re-asking, and verify via tooling.
